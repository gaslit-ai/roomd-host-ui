# §3 — Architectural problem statement (the 12 first principles)

> *Editorial note: §3 of the original report. Each principle is the spec-justified premise that one or more pieces of [the proposed architecture](./architecture/) builds on. Cross-link freely from architecture pages back here.*

The proposed architecture must be derived from these first principles, each justified against a specific spec, SDK, or repo source. "MUST" below means "required by this proposed architecture" unless a sentence cites a protocol requirement. See the citation catalog and subjectivity register in [sources.md](./sources.md).

**P1. Capability advertisement is a contract.**
A peer that includes `X` in its `capabilities` declaration must either register/route the methods covered by `X` or remove `X` from its declaration. The MCP lifecycle spec says peers operate according to negotiated capabilities, and the installed SDK guard chain (`client/index.js:347-453`) enforces missing capabilities as fatal in strict mode; advertising support but returning `MethodNotFound` later is the worst debuggability path. **Rationale:** consistency and debuggability. **Mechanism (proposed):** a `CapabilityBundle` factory that emits `(capability fragment, handler-registration callback)` as one indivisible pair; the `Client` is constructed by composing bundles, and TypeScript prohibits constructing a `Client` from a capabilities object without its corresponding handler set. See [MCP-LIFECYCLE](./sources.md#mcp-lifecycle), [SDK-CAPABILITY-GUARDS](./sources.md#sdk-capability-guards), and [capability bundles](./architecture/capability-bundles.md).

**P2. Tool execution is a single logical operation.**
Whether a call goes plain (`tools/call`) or task-augmented (`callToolStream`), whether it's invoked by the agent in chat-route or by a View through AppBridge, whether progress arrives via `notifications/tasks/status` or via `notifications/progress` ([§1.7](./spec/07-progress.md)), the user sees ONE operation with phases. **Rationale:** [§1.2](./spec/02-tools.md) + [§1.3](./spec/03-tasks.md) + [§1.6](./spec/06-mcp-apps.md) all converge on `CallToolResult`; the host's UX must converge similarly. **Mechanism (proposed):** a `Run` object — the supertype of "task or non-task tool call" — with phases `requested → input-streaming → started → progress* → input_required? → terminal`. See [Run abstraction](./architecture/run-abstraction.md).

**P3. Logical operations span the user, not the session.**
A task initiated by the agent on behalf of the user must be observable, cancelable, and inputtable from the user's active UI, including the browser tray. **Rationale:** the MCP tasks spec scopes task visibility by requestor authorization context, while this app currently also has separate client instances and in-memory registries. User-experienced tasks are therefore a host construct that need an explicit back-channel or shared access path. **Mechanism (proposed):** collapse browser+server MCP access through a server-proxied transport (recommended) OR push the chat-route's runs to the browser via SSE (alternative), so the tray sees runs from both sources. See [MCP-TASKS](./sources.md#mcp-tasks), [REPO-CHAT-ROUTE](./sources.md#repo-chat-route), [REPO-BROWSER-CLIENT](./sources.md#repo-browser-client), [topology](./architecture/topology.md), and [server-proxy](./architecture/server-proxy.md).

**P4. Tool outputs MUST be modeled per spec.**
`CallToolResult` has three meaningful pieces: `content[]` (model/user-visible blocks), `structuredContent` (machine output tied to `outputSchema`), and `isError` (tool execution error). A host that flattens these to `JSON.stringify(result)` loses semantics that the MCP tools spec and `@ai-sdk/mcp` preserve. **Mechanism (proposed):** `Run.toModelOutput` follows `@ai-sdk/mcp`'s pattern (`mcpToModelOutput`), and `Run.uiResult` exposes `{ content, structuredContent, isError }` separately to the renderer. `isError: true` does not throw, but is rendered with error styling and presented to the model as an error message. See [MCP-TOOLS](./sources.md#mcp-tools), [AI-SDK-MCP-MODELING](./sources.md#ai-sdk-mcp-modeling), and [tool result modeling](./architecture/tool-result-modeling.md).

**P5. Progress is a fan-in, not a fan-out.**
The host has *two* channels for "thing is making progress": `notifications/tasks/status` (when the call is task-augmented; [§1.3](./spec/03-tasks.md)) and `notifications/progress` ([§1.7](./spec/07-progress.md), ambient). They must funnel into the same `Run` observable. The message stream should write one logical AI SDK data part per Run, keyed by stable `type` and `id`, so AI SDK reconciles updates rather than appending duplicate parts. **Mechanism (proposed):** a single `RunRegistry.update(runId, patch)` invoked from both notification handlers; the `data-run` AI SDK part carries `{ runId, ... }`, while assistant-ui renders the resulting data part by `name`. See [MCP-PROGRESS](./sources.md#mcp-progress), [AI-SDK-DATA-UPDATES](./sources.md#ai-sdk-data-updates), [ASSISTANT-UI-DATA-RENDERING](./sources.md#assistant-ui-data-rendering), and [Run registry](./architecture/run-registry.md).

**P6. Tool annotations are first-class UX inputs.**
Spec [§1.2](./spec/02-tools.md) explicitly cautions hosts not to use annotations for security decisions, and separately recommends confirmation prompts for sensitive operations. Subjective design call: use `destructiveHint`, `idempotentHint`, and related annotations for confirmation flows and visual labeling while treating them as untrusted hints. Stripping them at the wrapper boundary (gap #6) discards useful display information. **Mechanism (proposed):** the wrapper preserves `title`, `annotations.*`, and `icons` and stamps them into the `Run.toolMeta`; the assistant-ui card and TaskTray read them. See [MCP-TOOLS](./sources.md#mcp-tools) and [tool result modeling](./architecture/tool-result-modeling.md).

**P7. AppBridge is the smallest legal interface for views.**
Per `ext-apps/src/app-bridge.js:assertTaskCapability("Tasks are not supported in MCP Apps")`, views MUST NOT initiate task-augmented requests. They send plain `tools/call` and receive `CallToolResult` (or cancellation). The host bridges. **Mechanism (proposed):** `AppBridge.oncalltool` ALWAYS routes through the host's `RunRegistry`, regardless of `taskSupport`. The view sees only the terminal `CallToolResult` (forwarded via `bridge.sendToolResult` + the spec-mandated `tool-input` ordering); the host chrome sees the full `Run.lifecycle`. See [host-app-bridge](./architecture/host-app-bridge.md).

**P8. Schema drives validation; validation drives UI.**
When `Tool.outputSchema` is declared, the server must return conforming structured results and clients should validate them; the installed SDK validates on both plain and task-stream paths. **Mechanism (proposed):** the wrapper compiles the JSON Schema at tool-list time, validates `structuredContent` on settle, and turns mismatches into `RunError("schema_validation")`, distinct from server-returned `isError`. See [MCP-TOOLS](./sources.md#mcp-tools), [SDK-CALLTOOL-VALIDATION](./sources.md#sdk-calltool-validation), [SDK-TASK-STREAM-VALIDATION](./sources.md#sdk-task-stream-validation), and [tool result modeling](./architecture/tool-result-modeling.md).

**P9. Memory and rate.**
The registry MUST prune terminal handles (gap #19) — keep N most-recent, drop the rest, expose a "history" buffer if needed. The registry MUST cap concurrent non-terminal Runs (gap #20). **Mechanism (proposed):** `RingBuffer<Run>` of size 128 for terminal history; admission control with a configurable limit (default 32 concurrent) that yields `429`-equivalent client-side errors when exceeded. See [Run registry](./architecture/run-registry.md#memory-and-rate-p9-gaps-19-20).

**P10. The View MUST be reachable for `tool-input-partial`.**
SEP-1865 §"Streaming" makes `ui/notifications/tool-input-partial` the official surface for streaming arguments. AI SDK emits `tool-input-delta` parts during `streamText`. The host MUST forward these to mounted Views by `toolCallId`. **Mechanism (proposed):** `RunRegistry` listens for AI SDK `tool-input-delta` and bridges to the matching `HostAppRenderer` via a host context fan-out. See [host-app-bridge](./architecture/host-app-bridge.md).

**P11. Single source of truth for the message-card.**
A `Run` produces one logical AI SDK data part with a stable `type` and `id`. AI SDK reconciles same-`type`/same-`id` data chunks before assistant-ui conversion; assistant-ui then renders data parts by `name` and the converted part data must carry `runId` because the converter drops the original AI SDK `id`. Today our writer emits separate progress and terminal part types, which can create duplicate logical rows (gap #13). **Mechanism (proposed):** writer emits one `data-run` part with `id = run.id`; subsequent writes use the same `type`/`id`, and the renderer reads `data.runId`. See [AI-SDK-DATA-UPDATES](./sources.md#ai-sdk-data-updates), [ASSISTANT-UI-DATA-RENDERING](./sources.md#assistant-ui-data-rendering), and [UI surface](./architecture/ui-surface.md).

**P12. Cancellation is bilateral.**
A user cancel from the tray MUST propagate to the chat-card (`isError: true`, terminal style; gap #14). The agent's downstream messages MUST not see a successful tool-call. AI SDK supports this via `signal: AbortSignal` on `execute`; we feed the registry's `AbortController` from the `Run.cancel()` and let AI SDK's stream see the abort. See [cancel-from-tray sequence](./architecture/lifecycle-sequences.md#cancel-from-tray).

These 12 principles form the architecture's spine.
